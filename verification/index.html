regex › I How matching works › Backtracking

31 steps · light · steps.json

  1. intro/intro — When greedy goes too far, the engine steps back.
  2. greedy-then-give-back/s01 — Pattern `a.*b`: an a, then `.*` (any character, as many as possible), then a b. Text: "aXbYb".
  3. greedy-then-give-back/s02 — Position 0 is an a. Pass: cursor 1.
  4. greedy-then-give-back/s03 — `.*` is **greedy**: it takes as much as it can. First the X: its run, the span it holds, is 1 character, and a **choice point** c1 remembers that.
  5. greedy-then-give-back/s04 — Then b, Y, b. The run holds 4 and the cursor is at the end of the text, position 5.
  6. greedy-then-give-back/s05 — The run asks for one more and finds no character left; that is a test, not a failure. The pattern moves on to b: 6 tries.
  7. greedy-then-give-back/s06 — Test b at position 5: nothing there. Fail, 7 tries.
  8. greedy-then-give-back/s07 — **Backtracking**: back to c1, the run gives one character back (now 3), and b is tested at position 4: a b. Match, 0 to 5, 8 tries.
  9. greedy-then-give-back/s08 — Note which b it matched: the last one. Greedy means the longest span that works, not the first b it could have stopped at.
  10. greedy-then-give-back/s09 — The **lazy** form `a.*?b` takes as little as it can. Reset: a passes, `.*?` takes nothing, and b is tested at position 1, an X: fail.
  11. greedy-then-give-back/s10 — Backtrack: the lazy run grows by one (the X), and b is tested at position 2: a b. Match, 0 to 3, the first b, in 4 tries.
  12. greedy-then-give-back/s11 — Both are correct; they answer different questions: the longest span, or the shortest. Every give-back is one more try.
  13. which-branch/s01 — Alternation is a choice too: in `(a|ab)c`, group 1 is a or ab, then a c. Text: "abc".
  14. which-branch/s02 — The engine takes the first branch, a, and saves choice point c1: the other branch, from position 0. The a passes and $1 is a.
  15. which-branch/s03 — Now c, at position 1: it is a b. Fail, 2 tries.
  16. which-branch/s04 — Backtrack: pop c1 and take the other branch from position 0. Its a passes; the group is open again, so $1 is empty.
  17. which-branch/s05 — Then b, at position 1: pass. Group 1 closes, and $1 is ab.
  18. which-branch/s06 — Then c, at position 2: pass. Match, 0 to 3, with $1 = ab, after 5 tries.
  19. which-branch/s07 — Each `|` and each quantifier is a place the engine may come back to. A few are cheap; many of them, nested, are not.
  20. blow-up/s01 — Pattern `(a+)+b` on "aaaX" looks harmless: some a, then a b. But the inner `a+` sits inside an outer `+`: two quantifiers on the same characters.
  21. blow-up/s02 — Run it to the end: no match, and the tries meter reads 38. The engine tried every way to split aaa between the two pluses, then every later start.
  22. blow-up/s03 — Same text, the plain pattern `a+b`: one quantifier. Run to the end: no match after 17 tries.
  23. blow-up/s04 — One more a, "aaaaX": nested 84 tries, plain 26.
  24. blow-up/s05 — Two more a, "aaaaaaX": nested 368 tries, plain 50. Each extra a about doubles the nested count; the plain count grows by a handful.
  25. blow-up/s06 — With 30 a characters in a row, the nested pattern needs about a billion tries (simplified). On a busy server, that is an outage.
  26. blow-up/s07 — Real outage: Cloudflare, 2019. One firewall rule ending in `.*.*=.*` pinned CPUs across the whole network for 27 minutes.
  27. blow-up/s08 — The fix: say what you mean. One quantifier per run of text, a class instead of `.*` (`[^"]*` cannot run past a quote), and anchors.
  28. blow-up/s09 — Or use an engine that never backtracks (RE2, Go, Rust regex): no blow-ups, but no backreferences. Rule: no nested quantifiers on untrusted input.

19 steps · light · dark · steps.json

  1. intro/intro — 122 random bits with a version and a variant.
  2. random-bytes/s01 — A **UUID** is 16 bytes. Start with 16 random bytes (we rolled them once for this lesson).
  3. random-bytes/s02 — Byte 6 (count from 0): its top 4 bits are replaced by 0100, the version, 4. So 07 becomes 47.
  4. random-bytes/s03 — Byte 8: its top 2 bits become 10, the variant, which says this is a standard UUID. So 2d becomes ad.
  5. random-bytes/s04 — Everything else stays random: 122 bits. Six fixed bits, 122 rolled ones.
  6. random-bytes/s05 — Write each byte as two hex digits, with dashes in an 8-4-4-4-12 pattern: 3fa85c12-9be4-4771-ad66-c0158af341b9.
  7. random-bytes/s06 — The third group starts with 4: the version. The fourth group starts with 8, 9, a or b: the variant bits 10.
  8. random-bytes/s07 — 122 random bits give about 5.3 × 10^36 ids. Two devices rolling at once will not collide in practice: odds, not a promise.
  9. random-bytes/s08 — No counter, no server, no clock. That is why every device can make its own id, and why the id says nothing about when or where.
  10. two-orders/s01 — Two devices, both offline. Each starts a new order and needs an id for it right now.
  11. two-orders/s02 — Each rolls its own v4 id. No request to a server, no shared counter.
  12. two-orders/s03 — Both come back online and send their orders to the server.
  13. two-orders/s04 — The server stores both. Different ids, no clash, and it never had to hand out numbers.
  14. two-orders/s05 — Whoops — with serial numbers, both devices would have said order 1001. Two orders, one key.
  15. two-orders/s06 — The fix: every device names its own things, and random names do not collide in practice. The CRDT course uses this for [op ids](/crdts/operation-based/every-device-needs-a-name).
  16. two-orders/s07 — One more thing: a v4 id tells you nothing, not when, not where. Good for privacy, bad for sorting, and that is where v7 comes in.
